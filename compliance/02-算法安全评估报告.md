## 第二部分：安全评估

### 2.1 信息发布安全

#### 2.1.1 内容输出审核机制

| 机制 | 实现 | 覆盖范围 |
|------|------|----------|
| 引用强制来源 | LLM 输出必须带 `[n] 法名 第X条`，引用从 RAG 召回 | 100% 输出 |
| 幻觉检测 | A3 Agent 逐字核对 [n] 引用是否真在召回文档中 | 100% 输出 |
| 自动剔除 | A3 标"幻觉"的引用自动过滤，不进入最终输出 | 100% 输出 |
| 置信度标注 | 每个回答带 confidence 分数（0-1） | 100% 输出 |
| 免责声明 | 顶部显著加"AI 分析仅供参考" | 100% 输出 |

#### 2.1.2 关键词过滤

LLM 输出前无关键词拦截层（依赖 A3 引用校验）。

**评估结论**：⚠️ 建议增加
- 添加涉政、涉暴、淫秽等敏感词拦截
- 但应避免过度拦截影响正常法律讨论
- 建议仅在最终输出端加敏感词二次扫描

#### 2.1.3 用户输入过滤

| 维度 | 现状 | 评估 |
|------|------|------|
| 输入长度限制 | 单次 4000 tokens | ✅ 合理 |
| 输入内容审计 | 无 | ⚠️ 建议加敏感词拦截 |
| 注入攻击防护 | 无（LLM 上下文） | ⚠️ 已知风险 |

**注入风险评估**：
- LLM 提示注入（Prompt Injection）确实存在风险
- 但因为律瞳是 RAG-based，最终输出仍受检索召回约束
- 攻击者无法通过提示注入获取未授权信息（无工具调用）
- 建议在用户输入前加敏感模式检测

### 2.2 数据安全

#### 2.2.1 数据分类

| 数据类别 | 敏感度 | 存储 | 加密 |
|----------|--------|------|------|
| 用户输入案情 | 中（可能含当事人姓名） | 不存储 | TLS 1.3 传输 |
| 用户会话 | 低 | 临时（进程内） | 无 |
| 法律知识库 | 无（公开） | Qdrant + SQLite | 无 |
| 类案判例 | 低（脱敏） | Qdrant + SQLite | 无 |
| LLM API Key | **高** | 服务器 .env | 文件权限 600 |
| SSH Key | **高** | /root/.ssh/ | 文件权限 600 |

#### 2.2.2 数据流转

```
用户案情
  ↓ TLS 1.3
Nginx (HTTPS)
  ↓
FastAPI 进程（内存中处理）
  ↓ HTTPS
MiniMax API（仅传案情 + 系统 prompt，不传用户身份）
  ↓
响应回 FastAPI（不存盘）
  ↓
返回用户浏览器
```

**关键点**：
- ✅ 案情不在服务器磁盘留痕
- ✅ 不传给 LLM 提供方任何用户身份信息
- ✅ MiniMax API 调用仅传案情内容 + system prompt
- ⚠️ 需在用户协议中告知"案情可能传输至 LLM 服务提供方"

#### 2.2.3 数据备份

| 数据 | 备份策略 |
|------|----------|
| 知识库源文件 | 已在 GitHub 备份（github.com/A-yiren/legal-lens） |
| 向量库 | 暂未自动备份（建议加每日 cron 备份 Qdrant collection） |
| 用户数据 | 不存储，无备份需求 |

- ✅ 无账号 = 无个人信息收集
- ⚠️ 未来如加账号体系，需同步做账号安全设计

### 2.4 服务稳定性

| 指标 | 现状 | 目标 |
|------|------|------|
| 可用性 | 99%+（单点故障风险） | 99.5% |
| 响应时间 | 60-90s（多 Agent 协同） | < 60s |
| 并发能力 | 5-10 QPS（单进程） | 取决于用户量 |
| 故障恢复 | 手动重启 2-3 分钟 | < 1 分钟 |

**单点故障**：阿里云 ECS 是单点，宕机即服务全断。
**建议**：
- 至少双实例部署
- 关键服务（LLM API、Qdrant）配置健康检查
- 准备故障切换脚本

### 2.5 合规专项

#### 2.5.1 标识规范（深度合成）

**评估**：律瞳不涉及深度合成（人脸、语音、图像生成），无需打 AI 生成标识水印。

#### 2.5.2 训练数据合规

**评估**：律瞳不训练任何模型，**无训练数据合规问题**。

#### 2.5.3 知识产权

| 内容 | 知识产权情况 |
|------|--------------|
| 26 部法律文本 | 公有领域（法律不享有版权） |
| 30 个判例 | 案情细节脱敏，案号格式属公有 |
| LLM 生成的"分析" | 律瞳拥有（用户输入 + 模型输出） |
| 用户输入案情 | 用户拥有，律瞳无使用权（除当次回答） |

#### 2.5.4 算法可解释性

律瞳采用多 Agent 协同 + 强制引用 + 引用溯源，**具有高度可解释性**：
- A1 / A2 / A3 / A4 各自职责明确
- 引用全部可点跳原文
- A3 幻觉检测明确告知哪些引用不可信

## 第三部分：评估结论

### 3.1 总体结论

**律瞳 LegalLens 在完成本报告所列改进项后，可满足生成式 AI 服务合规要求。**

### 3.2 必做改进项

1. ⏳ 加用户输入敏感词过滤
2. ⏳ 加输出端敏感词二次扫描
3. ⏳ 加首次访问用户协议确认弹窗
4. ⏳ 加未成年人年龄限制声明
5. ⏳ 加 Qdrant 向量库每日自动备份

### 3.3 建议改进项

1. 升级 LLM 多源容灾（MiniMax + 备用 API）
2. 加服务监控告警（响应时间 / 错误率）
3. 加用户反馈入口（输出页脚"反馈"按钮）
4. 双实例部署，消除单点故障

### 3.4 风险等级

**综合风险等级**：**中** （可接受，需完成必做项后上线）
